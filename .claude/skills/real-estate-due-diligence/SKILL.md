# 온라인 임장 멀티에이전트 리서치

사용자가 지역이나 아파트 단지 하나를 지정하면, 현장에 가지 않고도 최대한 현장에 가까운 수준으로 조사해서
부동산 초보자가 매수 의사결정을 할 수 있는 온라인 임장 리포트(단일 HTML 파일)를 만든다.

이 스킬은 검색 요약기가 아니라 리서치 오케스트레이터다. 조사 전략을 먼저 세우고,
영역별 전문 에이전트를 동적으로 편성해 병렬 조사시키고, 결과를 교차검증한 뒤 종합한다.

## 운영 철학 (모든 단계에 적용)

1. 정보량보다 의사결정 품질. 자료를 나열하지 말고 판단을 도와라.
2. 검색부터 하지 마라. "무엇을 알아야 하는가"를 먼저 정하고, 그 답을 가장 잘 아는 출처를 찾아라.
3. Fact(확인된 사실), Interpretation(사실 기반 분석), Hypothesis(검증 안 된 가설)를 절대 섞지 마라.
4. 장점과 단점을 같은 비중으로 다뤄라. Bull Case와 Bear Case는 필수다.
5. 모든 중요한 수치에는 출처와 기준일을 붙여라. 확인 못 한 것은 지어내지 말고 "확인 필요"로 남겨라.
6. 반대 증거를 의무적으로 찾아라. "내가 찾은 정보가 틀렸을 가능성"을 항상 검증해라.
7. 온라인으로 확인할 수 없는 것은 숨기지 말고 "현장 확인 항목"으로 분리해라.

## 진행 절차

### STEP 0. 준비
- 이 SKILL.md가 있는 디렉토리의 절대 경로를 `SKILL_DIR`로 잡는다. 에이전트 프롬프트에 넣을 레퍼런스 경로는 항상 절대 경로로 쓴다.
- `date +%F`로 조사 기준일 `AS_OF`를 확정한다. 워크플로 스크립트 안에서는 Date를 쓸 수 없으므로 반드시 여기서 확정해 args로 전달한다.
- 리포트 저장 경로는 현재 작업 디렉토리 기준 `reports/<대상>-온라인-임장-<AS_OF>.html`이다. 파일명의 공백은 `-`로 바꾼다.

### STEP 1. 요청 분석 (아직 검색하지 마라)
`references/research-framework.md`를 읽고 다음을 정한다.
- 조사 대상: 지역인가, 특정 단지인가. 일단 사용자 표기 그대로 적는다 (정규화는 STEP 3에서 한다).
- 조사 모드: `region`(지역 전체) / `complex`(단지 심층) / `candidate`(조건 탐색. 예산 내 후보 찾기) / `compare`(비교 중심) / `scenario`(장기 가치 시나리오). 판단 기준은 프레임워크의 "조사 깊이 자동 결정" 절이다.
- 사용자 목적 단서: 실거주, 투자, 예산, 자녀 교육, 직주근접 등. 명시가 없으면 특정 목적을 가정하지 말고, 리포트에서 실거주 관점과 자산가치 관점을 분리해 다루기로 한다.
- 대상이 근본적으로 모호할 때만 (예. 같은 이름의 동이 여러 지역에 있고 문맥으로 특정 불가) 사용자에게 물어라. 그 외에는 질문 없이 진행한다.

### STEP 2. 조사 질문 생성
프레임워크의 영역 A~G와 매수자 핵심 질문을 바탕으로 이 대상에 맞는 조사 질문 목록을 만든다.
`지역 → 조사 질문 → 필요한 데이터 → 최적 출처 → 수집 → 검증 → 분석 → 판단` 순서를 지킨다.

### STEP 3. 정찰 (가벼운 검색 2~4회)
WebSearch로 다음만 빠르게 확인한다. 본조사는 에이전트가 한다. WebSearch가 도구 목록에 없으면 `ToolSearch("select:WebSearch,WebFetch")`로 로드한다.
- 대상 정규화: 정확한 행정구역(시/구/동), 단지면 정식 명칭과 소재지.
- 지역 특성 파악: 재건축/재개발 밀집 여부, 학군지 여부, 침수 이력, 신축 공급, 그 지역만의 특수 이슈.
- 이 결과로 전문가 편성과 추가 조사 영역을 확정한다 (예. 정비사업 밀집이면 정비사업 전문가 강화, 저지대면 재해 리스크 강화).

### STEP 4. 멀티에이전트 워크플로 실행
`references/workflow-guide.md`를 읽고, 이번 대상에 맞는 워크플로 스크립트를 작성해 Workflow 도구로 실행한다.
- 편성은 동적으로 한다. 기본 로스터에서 시작하되 정찰 결과에 따라 전문가를 추가하거나 뺀다. 고정 목록을 기계적으로 돌리지 마라.
- args로 `{ target, address, mode, asOf, skillDir, traits, purposeHint, budgetHint }`를 실제 JSON 값으로 전달한다.
- 실행 직전에 사용자에게 조사 전략을 3~5줄로 알린다 (대상, 모드, 편성, 예상 산출물). 허락을 구하지 말고 알리기만 해라.
- 워크플로는 백그라운드로 돌고 완료 알림이 온다. 완료 전에 결과를 예측하거나 지어내지 마라.
- Workflow 도구가 없는 환경이면 같은 편성과 프롬프트를 Agent(또는 Task) 병렬 호출로 재현한다. 폴백 방법도 workflow-guide.md에 있다.

### STEP 5. 갭 점검과 보강
워크플로가 반환한 완결성 감사(gaps) 결과를 검토한다.
- 매수 판단을 좌우하는 구멍(예. 실거래가 미확인, 정비사업 단계 미확인)이 있으면 보강 에이전트를 띄운다. 보강은 1라운드로 제한한다.
- 사소한 구멍은 리포트의 "확인 필요"와 한계 섹션에 명시하는 것으로 갈음한다.
- 결과가 비어 보이면 워크플로 transcript 디렉토리의 `journal.jsonl`을 읽어 각 에이전트의 실제 반환값을 확인해라.

### STEP 6. HTML 리포트 작성
`references/html-report-guide.md`와 `templates/report-template.html`을 읽고, 워크플로 결과를 바탕으로 오케스트레이터가 직접 리포트를 작성한다.
- 템플릿의 수치와 문구는 전부 자리표시자다. 조사 데이터로 완전히 교체한다.
- 근거 없는 섹션은 만들지 마라. 데이터가 없으면 섹션을 빼고 한계에 기록한다.
- 용어가 처음 나오면 초보자용 설명 박스를 붙인다. 정의는 `references/real-estate-glossary.md`를 따른다.
- 리포트에 넣는 링크는 조사 과정에서 실제 확인된 URL만 쓴다.

### STEP 7. QA
리포트 저장 후 html-report-guide.md의 Content QA / UX QA / Investment QA 체크리스트로 검수한다.
- 가능하면 별도 QA 에이전트를 하나 띄워 저장된 HTML 파일을 새 눈으로 검수시키고, 지적을 반영한다.
- 실거래와 호가 구분, 개발계획과 확정 구분, 출처와 기준일 누락을 중점 점검한다.

### STEP 8. 최종 출력
사용자에게는 간결하게 알린다. 형식은 html-report-guide.md의 "최종 사용자 메시지" 절을 따른다.
(대상, 기준일, 한 줄 결론, 주요 발견 3개 내외, 가장 중요한 리스크, 리포트 파일 경로)
파일 전송 도구(SendUserFile 등)가 있으면 리포트 파일을 함께 전송한다.

## 조사 깊이와 규모

- 사용자가 "가볍게", "빠르게"라고 하면 전문가를 4~5명으로 줄이고 검증을 축소한다.
- 사용자가 "철저히", "깊게"라고 하면 전문가와 검증 인원을 늘린다.
- 별도 언급이 없으면 모드별 기본 편성(workflow-guide.md)을 따른다. 기본 규모는 에이전트 15~20개 안팎이다.
- 모델 라우팅: 수집/검증 에이전트는 sonnet으로 지정하고, Bull/Bear와 최종 판단은 지정 없이 세션 모델을 상속시킨다. 상세 기준은 workflow-guide.md의 "모델 라우팅" 절을 따른다.

## 하드 룰 (위반 금지)

- 호가를 실거래가처럼 쓰지 마라. 실거래, 호가, 추정가를 항상 구분해라.
- "개발 예정" 문구만으로 호재라고 쓰지 마라. 사업 단계와 공식 발표를 확인해라.
- 블로그 하나, 기사 제목 하나로 결론 내리지 마라.
- 출처 없는 숫자를 만들지 마라. 로드뷰로 확인하지 못한 것을 확인했다고 쓰지 마라.
- "무조건 오른다", "무조건 사야 한다" 같은 표현을 쓰지 마라. 최종 판단은 `매수 고려 / 적극 검토 / 관망 / 비추천` 중 하나로, 근거 3~5개와 함께 제시해라.
- 전체 금지 목록은 `references/verification-guide.md`에 있다. 리포트 작성 전에 반드시 확인해라.

## 도구 메모

- 오케스트레이터와 에이전트 모두: WebSearch, WebFetch가 도구 목록에 없으면 `ToolSearch("select:WebSearch,WebFetch")`로 로드해서 쓴다.
- 로드뷰/지도 실사는 브라우저 자동화 도구가 가용할 때만 오케스트레이터가 워크플로 종료 후 직접 수행한다. 병렬 에이전트에 맡기지 마라 (탭이 충돌한다). 불가하면 리포트 한계에 명시한다.
- 지도/로드뷰 화면을 무단 캡처해서 리포트에 넣지 마라. 위치 관계는 직접 그린 SVG 개념도로 표현하고, 실제 지도는 딥링크로 제공한다.
